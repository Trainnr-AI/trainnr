# Isaac Lab Arena: environment definition and agentic environment generation

*Fifth pass, 2026-08-26. One agent, one field, against a single primary
source: a repomix bundle of the whole `isaaclab_arena` repository
(*scratchpad/arena.md*, 132,303 lines). Tests [docs/30-the-full-loop.md](../30-the-full-loop.md)
§3.6 (coding agents write the leaves, gates judge them) and §3.1/①
(scenes are programs) against the one shipping system that already has
an LLM writing evaluation environments behind validation gates.
Citations are `repo/path.py · arena.md:LINE`: the file inside Arena's
tree, and the bundle line where the quoted text sits. Nothing below
comes from memory; every claim has a line.*

---

Terms used throughout, defined once here and again where they first matter:
**Isaac Lab** is NVIDIA's GPU robot-learning framework on Isaac Sim; its
environments are "manager-based" (observations, actions, events, terminations
each configured by a manager). **USD** is the scene file format Isaac Sim
loads; a **prim** is one node in a USD scene tree. **Pydantic** is a Python
library that validates data against typed classes and emits a JSON schema
from them. A **registry** here is a name→class dictionary filled by decorators.
**MjSpec** is MuJoCo's programmatic model-building API — what our task builders
use instead of XML. A **bundle** on our side is a directory identified as
`name@hash` (`trainnr/bundles/hashing.py::stamp`).

## 1. What Arena does

### 1.1 An environment is three parts, compiled by a builder

- An environment is **scene + embodiment + task**: "Arena environments are composed of three independent sub-pieces" (`docs/pages/concepts/environment/index.rst · arena.md:4958`). The container is `IsaacLabArenaEnvironment(name, scene, embodiment, task, teleop_device, env_cfg_callback, rl_framework_entry_point, rl_policy_cfg, episode_recorder_terms, placer_params)` (`isaaclab_arena/environments/isaaclab_arena_environment.py · arena.md:32379-32391`) — ten constructor arguments, of which the YAML spec below can fill five (`environment_definition.rst · arena.md:4733-4736`).
- Each component contributes a partial config per Isaac Lab manager: scene gives "assets, lights"; embodiment "robot, sensors / proprioception, cameras / control interface / robot reset"; task "success, failure" terminations, "dense rewards (RL)", "metrics-required data" (`env_builder.rst · arena.md:4468-4487`).
- `ArenaEnvBuilder.compose_manager_cfg()` merges them with `combine_configclass_instances("SceneCfg", …scene.get_scene_cfg(), embodiment.get_scene_cfg(), task.get_scene_cfg())` and likewise for observations, events, terminations, metrics, recorders (`arena_env_builder.py · arena.md:31988-32098`). Order matters and is stated: "Solve relations before building scene config so positions are captured correctly" (`arena.md:31968-31970`), and "Reachability constraints are defined in the task, so apply them before placement" (`arena.md:31843-31845`).
- The task contract is small: `TaskBase` requires `get_scene_cfg`, `get_termination_cfg`, `get_events_cfg`, `get_mimic_env_cfg`, `get_metrics` (`isaaclab_arena/tasks/task_base.py · arena.md:49497-49515`); optional hooks default to `None`. A task also declares what its success *means* as data: `success_state_transition()` returns a `TaskTransition` whose effects are only two kinds — "`Relocate` — a node moves into a spatial relation with another node" and "`SetState` — a node's own state changes in place" (`tasks/task_transition.py · arena.md:49609-49614`). `PickAndPlaceTask.__init__(pick_up_object: Asset, destination_location: Asset, background_scene: Asset, destination_object=None, episode_length_s=None, task_description=None, force_threshold=0.1, velocity_threshold=0.1, max_separation=None, …)` (`tasks/pick_and_place_task.py · arena.md:48232-48244`) and it stamps reachability on exactly its two targets (`arena.md:48266-48268`).
- Two independent seeds: `--seed` (default 42) fixes "reset noise and run-time variation draws"; `--placement_seed` (default `None`, unlocked) fixes "relation-solver layouts and random RigidObjectSet member assignment"; "There is no variation seed" (`env_builder.rst · arena.md:4517-4534`).
- The compiled config is `gym.register`ed under the environment name and `gym.make`d (`arena_env_builder.py · arena.md:32236-32241, 32298`).

### 1.2 External repos add environments, tasks, embodiments without touching Arena

- Recommended integration: "an **unmodified git submodule** … extend it purely through its registration API" (`docs/pages/arena_in_your_repo/external_installation.rst · arena.md:3380-3382`).
- An external environment subclasses `ExampleEnvironmentBase`, sets `name`, implements `get_env()` and `add_cli_args()` (`external_environments.rst · arena.md:3268-3269`); it is run by `--external_environment_class_path my_package…:ExternalFrankaTableEnvironment franka_table --object tomato_soup_can` (`arena.md:3329-3334`).
- A custom task subclasses `TaskBase` (a 50-step success example at `arena.md:3480-3496`); a custom embodiment subclasses an existing one and is `@register_asset`ed under a new `name` (`external_tasks_and_embodiments.rst · arena.md:3519-3523`). Registration decorators are one-liners that refuse duplicates with a `WARNING` (`isaaclab_arena/assets/register.py · arena.md:25778-25783`); tasks are keyed by `cls.__name__` "so the YAML `type: PascalCase` lookups match" (`arena.md:25846-25853`).

### 1.3 The environment spec: `ArenaEnvGraphSpec`

The same environment can be a registered Python factory (`@register_environment class … (ArenaEnvironmentFactory)` with `build(cfg)`) or a YAML graph; "Both produce the same object" (`environment_definition.rst · arena.md:4591, 4597-4602`). The YAML is a Pydantic model, "the single source of truth for scene layout and tasks" (`isaaclab_arena/environment_spec/arena_env_graph_spec.py · arena.md:30942`):

| Field | Type / rule | Where |
|---|---|---|
| `env_name` | non-empty snake_case label | `arena.md:30944` |
| `embodiment`, `background` | `AssetSpec(id, registry_name, params)`; `registry_name` must be registered: `assert AssetRegistry().is_registered(registry_name)` | `arena_env_graph_types.py · arena.md:31337-31359, 31328` |
| `objects` | list of `AssetSpec`, "Movable scene objects, including distractors" | `arena.md:30947` |
| `object_sets` | `ObjectSetSpec(id, members, random_choice, params)`; members must be registered *rigid* objects — one member per parallel env | `arena.md:31379-31418` |
| `object_references` | `ObjectReferenceSpec(id, parent_id, prim_path, object_type, params)` — a prim *inside* the background exposed as a node; "Nothing is spawned for it" | `arena.md:31430-31447`; `arena.md:8460-8462` |
| `relations` | `SpatialRelationSpec(kind, subject, reference, params)`; kind must be registered; unary kinds must have no `reference`, binary kinds must | `arena.md:31513-31561` |
| `task` | `CompositeTaskSpec(composition ∈ {atomic, parallel, sequential}, description, subtasks)`; `atomic` ⇒ exactly one subtask, else ≥2 | `arena.md:31483-31510` |
| `task.subtasks[]` | `TaskSpec(kind, params)`; `kind` must be in `TaskRegistry` | `arena.md:31450-31472` |
| `placement_validators` | `PlacementValidatorSpec(enabled_checks, required_checks, debug_visualize, debug_visualize_output_path)`; built-ins "no_overlap, on_relation, next_to, not_next_to, face_to"; `required ⊆ enabled`; debug streams candidate layouts "to a spawned Rerun viewer window" | `arena.md:31583-31627` |
| `cli_override_specs` | `CliOverrideSpec(arg, target_node_id)` — a YAML-declared CLI flag that swaps a node's `registry_name` | `arena.md:31630-31640` |

Cross-cutting rules, all enforced at load (`from_yaml()` → `model_validate`):
- Unique ids across embodiment/background/objects/object_sets/references; reference parents must be the background or an object; relation endpoints and *every string-valued task param* must name a known node id (`arena_env_graph_spec.py · arena.md:30977-31040`).
- Which task params are node references is read from the task class's own `__init__` type hints: params annotated `Asset` or `AffordanceBase` (or `list[…]` of them) are resolved to live assets, "The task class is the single source of truth for which params come from graph nodes" (`arena_env_graph_task_conversion_utils.py · arena.md:31147-31151, 31208-31210`).
- `external_yaml` includes one scene file into many task files; "no nesting", and "Duplicate env graph spec key across includes" is an error (`arena_env_graph_yaml_loader.py · arena.md:31659-31703`).
- Defaults the loader adds: an object's `instance_name` defaults to its node id (`arena.md:30853`); an `is_anchor` subject with no pose gets `Pose.identity()` (`arena.md:30901-30902`); if no light exists in the scene or the background USD, a dome light and an (off) directional light are injected (`arena.md:30775-30800`).
- The docs are explicit that this is the payoff of YAML over Python: "Registry names, node ids, relation arity, task params, and check subsets fail when the file loads — before Isaac Sim starts. Python has no equivalent" (`environment_definition.rst · arena.md:4812-4815`).

### 1.4 The agent: prompt → validated spec, gated at every step

`EnvironmentGenerationAgent.generate_spec(prompt, asset_catalog, relation_catalog, task_catalog) -> (spec | None, data | None)` (`isaaclab_arena/agentic_environment_generation/environment_generation_agent.py · arena.md:19496-19546`). Arena's own framing: "Arena does not reason about the scene. It builds a prompt from the catalogs, asks the model for a JSON object matching the ArenaEnvGraphSpec schema, and validates the result" (`model_selection.rst · arena.md:4113-4115`).

1. **Catalogues from live registries.** `build_asset_catalogue` classifies registered classes by their `tags` into embodiments/backgrounds/objects (`catalogues.py · arena.md:19164-19179`); relation and task catalogues include only classes where `getattr(cls, "agent_ready", False)` (`arena.md:19232, 19289-19294`). `@agent_ready` is literally `cls.agent_ready = True` (`register.py · arena.md:25857-25860`) — an allow-list, not a capability. Required/optional/enum params are read by introspecting `cls.__init__` (`_collect_init_params`, `arena.md:19333-19360`) and printed as e.g. `- PickAndPlaceTask (required: …; optional: …): <first docstring line>` (`arena.md:19282-19285`). Today only pick-and-place and open/close door are exposed (`agentic_environment_generation/index.rst · arena.md:4066-4071`).
2. **Structured output with a strict schema.** `build_strict_schema` takes the Pydantic JSON schema and sets `additionalProperties = False`, makes every property required, and drops `default` (`inference_backend.py · arena.md:19855-19908`); the call uses `response_format={"type": "json_schema", …}` (`arena.md:19810-19816`). Transport retries: `max_retries=3` fresh calls on network / empty-response / malformed-JSON (`arena.md:19803-19841`); the endpoint is pinged once at construction (`arena.md:19870-19893`).
3. **Critic loop, capped at three.** `MAX_SPEC_INFERENCE_CALLS = 3` (`spec_inference.py · arena.md:20566`). Each response goes through `ArenaEnvGraphSpec.model_validate` *and* `collect_agent_ready_validation_trace` (`arena.md:20617-20624`); on failure the next user message appends "CRITIC FEEDBACK: The previous response failed validation. Regenerate the complete ArenaEnvGraphSpec, correcting every error below" plus the error lines and the rejected JSON (`arena.md:20641-20662`). The second gate checks the model's answer against the *exact* vocabulary it was shown: every `registry_name` in the catalogue block it belongs to, every task/relation `kind` in its catalogue, required params present, "anything outside required|optional is rejected" (`spec_validation.py · arena.md:20839-20907`).
4. **The system prompt is the design doc.** Rules include: "Do NOT hallucinate asset names — every registry_name must appear verbatim in the catalog"; "pick task.composition from the number of subtasks you emit"; "Task parameters referring to an asest … must use the ID (NOT registry_name)"; "include an is_anchor relation on the resting surface"; "All objects need an on relation with that anchor" (`arena.md:20680-20721`).
5. **Prim-path resolution, one call, no critic loop.** If the spec has `object_references`, `PrimPathInference` loads the background USD's prim tree, first *forces* each reference's `object_type` from its task role (open/close targets → articulation, pick targets → rigid, else base — `prim_path_inference.py · arena.md:20201-20234`), asks the model for paths from a printed tree, then asserts every path "is … in the background prim tree" and that rigid/articulation types match the tree (`arena.md:20237-20254`). The docs: "There is no critic loop here" (`system_overview.rst · arena.md:4281-4282`). Prompt cost: "about 30 000 characters (10 000 tokens) for lightwheel_robocasa_kitchen (886 prims)" (`model_selection.rst · arena.md:4139-4141`).
6. **Optional asset search.** `MissingObjectInference` asks which prompt objects the catalogue lacks, at most `MAX_SEARCH_PHRASES = 8` ("a prompt that needs more than this is asking for a scene, not a manipulation task", `missing_object_inference.py · arena.md:19945-19947`); SimReady (NVIDIA's physics-annotated USD library) hits are kept only if the USD has exactly one rigid body (`simready_asset_search.py · arena.md:20483-20502`); unmatched phrases are reported as `unavailable_objects` and "the spec is built without them" (`arena.md:19486-19494`). Found objects are rewritten to the portable `simready_usd_object` entry with `params["usd_path"]` because "A search name only exists in the process that searched" (`arena.md:19548-19572`).
7. **Outputs are honest either way.** Success: `(spec, None)`; failure: `(None, data)` and `agent.traces` (`arena.md:19514-19518`). A rejected spec is written as `invalid_<env_name>.yaml` with the traces as YAML comments above it (`spec_io.py · arena.md:20744, 20772-20791`).

Measured quality and its limits, in Arena's words: public `openai/gpt-oss-120b` 13/15 (86.7%) at 22 s mean; `gpt-5.6-terra` 15/15 at 10–12 s — "five documented prompts three times", "snapshots rather than guarantees" (`model_selection.rst · arena.md:4159-4188`). "Output is non-deterministic, even at --temperature 0. Validation only proves a spec is admissible, not that it is the environment you asked for" (`arena.md:4193-4194`). "The reviewed YAML can be used to reproduce the environment, but re-running the prompt to create the environment is not" (`arena.md:4210`). Non-goals: "Asset generation" and "Motion generation" (`index.rst · arena.md:4078-4087`). Weak-model failure modes: "invent asset names / drop objects / anchor the scene to the background instead of the counter / collapse five parallel pick-and-places into one atomic task" (`arena.md:4131-4134`).

### 1.5 Runners: the CLI's six modes and the review GUI

- `cli_runner.py --mode {schema, catalog, prim_tree, resolve, build, full}`; the first three "make no agent call" and start no simulator (`isaaclab_arena_examples/agentic_environment_generation/cli_runner.py · arena.md:110851-110863`). `build` loads the YAML, `to_arena_env()`, `ArenaEnvBuilder(...).make_registered()`, then runs `ZeroActionPolicy` for `--num_steps` (default 20) as a smoke test (`arena.md:110893-110897, 111089-111125`). The recommended human loop is `resolve` → edit → `build` (`cli_runner.rst · arena.md:3699-3712`).
- The GUI is "a Streamlit live editor" (Python web-UI library) with a prompt panel, a YAML editor that "validates the YAML as you work", a searchable "background prim-tree panel", a graph dashboard, and a "Sim preview" that runs construction, relation solving, and a zero-action rollout "in a SimulationApp side process" and records the viewport (`gui_runner.rst · arena.md:3821-3823, 3872-3877, 3910-3914`). On failure "the invalid YAML is still loaded into the editor and the validation traces are shown alongside it" (`arena.md:3864-3866`).
- What only the simulator catches: "Objects intersecting geometry, or a robot that cannot reach the task objects, show up here and nowhere in validation" (`model_selection.rst · arena.md:4207-4208`). The build-time placement report reads `passed per check: on_relation=49/50, next_to=45/50, …, ik_reachable=15/44` (cuRobo, NVIDIA's GPU IK library, only in that container), and "When an environment finds no reachable layout at all, it falls back to its lowest-loss layout" (`kitchen_pick_and_place/step_3 · arena.md:8652-8656`; the "best-loss fallback layouts" warning at `relation_solver_interface.py · arena.md:32898-32902`).
- The kitchen example shows the residual human work even on a passing spec: the prompt "does not identify which countertop to use, and the kitchen contains five candidate counter surfaces" (`step_2 · arena.md:8467-8470`), and the robot's `next_to` side and a `rotate_around_solution` yaw were set by hand (`arena.md:8525-8544`).

## 2. What we already have that is equivalent

- **Scene + task as a program.** `trainnr/tasks/aloha2/kitting.py::_rig_scene` loads the bundle `aloha2.xml` as `mujoco.MjSpec`, `_task_scene` applies a `look`, `build_kitting` adds slot walls, two free boxes (`_add_free_box`), the `top` camera and `referee/*_gripper_pos` framepos sensors (`_add_top_camera_and_referees`), and returns `ALOHA2Task(name, spec, protocol, cameras)`. That is Arena's Scene + Task in one function; the embodiment is the bundle itself. `tasks/components.py::compose` already does Arena-style composition (car alone, arm alone, arm on car).
- **The protocol object.** `trainnr/evaluate/harness.py::EpisodeProtocol(trials, steps, control_interval, perturb, success, home)` is our `TaskSpec` + termination + episode length; `perturb(trial, home)` is keyed by trial index so trials are paired across policies (Arena's `placement_seed` role, but deterministic by construction); `home` names the bundle keyframe (docs/31 §2).
- **Gates.** `score_policies` refuses duplicate policy names and any `source` without `@hash`, then census-gates via `robot/model_checks.py::assert_model_alive(actuators, sensors, geoms, cameras)` — the equivalent of Arena's "fail before the simulator starts", at the model level. `bundles/profile.py::load_profile` rejects unknown keys ("a misspelled field would otherwise fall back to a default and lie quietly") — the same posture as Pydantic strict mode, in stdlib.
- **Identity.** `bundles/hashing.py::stamp` gives `name@hash`; Arena has no content hash on a spec — its reproducibility claim rests on "the reviewed YAML", unhashed.
- **The agent layer as practice.** docs/30 §3.6: agents write scene programs, protocols, referee sensors, adapters; three rules (never grade own output; artifacts not forks; envelope off-limits). docs/33's verdict added verifier co-evolution and counterexample-as-feedback — which is exactly Arena's critic loop.
- **Smoke test.** The "limp" floor policy in every harness ladder is Arena's zero-action policy; `tools/kitting-demos.py` filters demos through the referee.

What we do not have: a declarative spec at all (tasks are Python); any catalogue of what an agent may use; any load-time cross-reference check (a misspelled geom name in a referee dies inside MuJoCo, not at the boundary); any placement/reach check before episodes are spent (spawn bands are hand-measured constants, `PART_SPAWN`).

## 3. Adopt / skip

### Adopt

1. **A task spec, validated at load, hashed as an artifact.** `trainnr/tasks/spec`: a stdlib dataclass (same reason as `RobotProfile` — the bundles layer stays dependency-free) loaded from YAML with fields `bundle` (`name@hash`), `look`, `bodies[] (id, kind: box|…, half, rgba, contact, home)`, `fixtures[]` (static geoms such as slot walls), `cameras[]`, `referees[] (id, sensor type, target geom/site)`, `relations[] (kind, subject, reference, params)` limited to what `perturb` can realise (`is_anchor`, `on`, `spawn_band`, `next_to`), `task (kind, params)` where every string param must be a node id, and `protocol (trials, steps, control_interval, home, hold_steps)`. The builder turns it into the `MjSpec` that `build_kitting` builds today. Load gates, in Arena's order: (a) unknown keys → error; (b) unique ids, every relation endpoint and task param names a node; (c) `task.kind` in a task registry and its required/optional params read from the success builder's signature (`_collect_init_params` pattern, `arena.md:19333-19360`); (d) bundle names exist — `home` is a keyframe in the bundle, every referee target and camera name resolves through `mj_name2id` on the *compiled* model, the analogue of Arena's prim-tree check (`arena.md:20237-20254`). The written spec is stamped `task-<name>@hash` and cited by every certificate — closing the gap Arena leaves open (§2, identity).
2. **The agent loop shape, without the LLM backend.** Our coding agent edits the YAML (and only the YAML) in a `resolve` step; a `build` step compiles, census-gates, runs the limp policy for N steps, and *then* the scripted expert under the protocol — success from the referee, never from the author (rule 1). Feed the gate's trace lines back as the next prompt, cap at three rounds (`MAX_SPEC_INFERENCE_CALLS`, `arena.md:20566`), and on failure write `invalid_<name>.yaml` with the traces as YAML comments (`arena.md:20772-20791`) so the operator can fix it without re-prompting. Keep Arena's honesty outputs: an `unavailable` list for anything the prompt asked for that the catalogue cannot supply (`arena.md:19486-19494`).
3. **A catalogue that costs nothing.** `--mode schema | catalog | bodies` printing the spec schema, the task/relation/referee vocabulary, and the bundle's body/site/geom/camera/keyframe tree (Arena's `prim_tree`, `arena.md:111032-111051`) — so an agent picks names from a printed tree instead of guessing, and the gate checks them against that same tree. `@agent_ready` becomes an explicit allow-list on our task builders; it costs one attribute (`arena.md:25857-25860`).
4. **A placement gate with per-check counts.** Before any episode: at each paired start, `mj_forward` and refuse penetrating contacts (what the kitting work found by hand), and run `robot/arm_ik.py::solve_arm_ik` to the grasp target at every spawn corner; print `passed per check: no_overlap=4/4, reachable=3/4` in Arena's format (`arena.md:8652`). Fall back never — a spec whose starts are unreachable is invalid, not "lowest-loss" (`arena.md:8656` is the behaviour to avoid under a certificate).
5. **Split the agent's write scope the way Arena splits it.** Agent-generated: the spec (objects, fixtures, relations, task kind + params, protocol numbers). Hand-written and registry-gated: success predicates (`success(states, sensors)` bodies, thresholds like `_PART_IN_SLOT_XY_M`), referee sensor kinds, scripted experts and IK choreography (`kitting_waypoints`), and every physics number (the bundle). This is Arena's own line — no asset generation, no motion generation (`arena.md:4078-4087`) — and our rule 3.

### Skip, with reasons

- `InferenceBackend`, endpoint presets, `response_format=json_schema` (`arena.md:19635-19841`): our agent layer is a coding agent writing files under operator review, not a JSON-emitting model behind an HTTP client. The *gates* transfer; the transport does not.
- The relation solver and pooled placement (`PooledObjectPlacer`, `min_unique_layouts_per_env`, `relation_solver_interface.py · arena.md:32887-32893`): our certificate needs paired, deterministic starts (`perturb` by trial index); a sampled pool breaks pairing. If layout variety is ever needed, index a fixed pool by trial rather than adopting the solver.
- USD prim-path inference and SimReady search (`arena.md:20024-20537`): no USD, no asset library; our assets are MjSpec primitives and Menagerie bundles. The `bodies` catalogue (adopt 3) covers the same need.
- The Streamlit GUI (`arena.md:3816-3952`): Rerun + the MuJoCo viewer are our review surface (every rig session gets both); the GUI's one transferable behaviour — invalid YAML shown beside its traces — lives in the CLI output.
- Isaac Lab manager composition (`combine_configclass_instances`, `arena.md:31988-32098`), default-light injection (`arena.md:30775-30800`), `object_sets` per parallel env (`arena.md:31379-31418`), mimic mode (`arena.md:32131-32162`): MjSpec is already our composition layer; `look` handles lighting; the harness has no parallel envs; LeRobot and scripted experts cover data generation.

## 4. Open questions

1. Arena declares what success *means* as data (`TaskTransition`: `Relocate` / `SetState`, `arena.md:49609-49614`) while the predicate stays code. Should our spec carry a declarative `success` (`in_slot: {node, slot, xy_m, z_m}`) compiled to today's predicates? It would make success spec-checkable and agent-untouchable at once — but then the thresholds are agent-written numbers, and rule 1 has to say who owns them.
2. Arena's acceptance number is "spec matched the expected structure" (13/15, `arena.md:4185-4186`), which the docs themselves call insufficient (`arena.md:4193-4194`). What is ours? Proposed: a spec is accepted only when gates (a)–(d) pass *and* the scripted expert clears a declared floor on the paired trials — the referee as reviewer of the agent.
3. Which artifact is hashed: the YAML, the compiled MjSpec XML, or both? The XML is what physics ran; the YAML is what the agent wrote. A certificate probably cites both (`task@hash` over the YAML, and the compiled model's hash beside the bundle's).
4. Reach at four corners versus Arena's 50-candidate `ik_reachable` pool (`arena.md:8652`): is corner coverage enough evidence that the whole band is reachable, or does the placement gate need to sample the band once at spec time and record the pass ratio?
5. Arena's variations (build-time and run-time, Hydra overrides, `arena.md:31871-31923`) and its metrics/recorder managers are another field's report; the spec above should leave a `variations` key unfilled rather than invent one.
